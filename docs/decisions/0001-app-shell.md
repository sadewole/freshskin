# 0001 — A framework-free PWA shell instead of Next.js

- **Status:** accepted
- **Date:** 2026-11-12

## Context

The product spec asks for a Next.js app. The development and verification environment cannot
dlopen native binaries, and Next's SWC compiler is one. A Next app could not be built or
verified here, so following the spec literally would have produced source no one could run.

## Decision

Build the HTTP layer as a small Node `http` server (`app/server.ts`) and the client as a Vite +
React single-page app (`web/`). The server serves both `/api/v1` and the built SPA from
`app/public`, so cookies, CSP, and the service-worker scope stay same-origin.

The routes in `app/server.ts` are deliberately thin: parse the request, call a service in
`src/service/` or `src/http/`, and present the response. They own no policy. That makes them a
straightforward port target if a Next.js or other framework shell is adopted later.

## Consequences

- One fewer build-time native dependency, and the whole app can be built and tested here.
- No Next.js file-system routing, server components, or image optimisation. Routes are
  registered explicitly and the SPA uses a small in-repo router.
- The `app/` directory holds the server, not the frontend. The frontend source lives in `web/`;
  `app/public` is generated by `pnpm web:build`.
- Revisit this decision if the deployment target can run Next.js and its routing or server
  rendering becomes valuable.

## Status

Superseded in part (2026-11-14): the single-origin serving model is replaced by the
three-origin split in `docs/design/ui-workflow.md` §7. The thin-route principle and the
`apps/api` service/presenter layering stand. Record kept for the rationale.
